# Rounded content and coordinated sidebar geometry

Date: 2026-11-01. Status: bounded real-host acceptance passed.

The opt-in Chromium-connected workspace host now has one per-window engine geometry state for sidebar width and mode. Docked mode reserves the requested width in Chrome’s child layout. Hidden mode removes that reservation and retains only a six-point native tracking edge. Transient reveal overlays the sidebar at its retained width without reserving page space. Requested width defaults to 260 points and clamps to 220–400 points; actual native bounds and the Chrome reservation clamp together to the available client width while retaining 320 points for Chrome content. Docked minimum sizing includes the requested reservation. Geometry is session-local and is not persisted in the organization document.

The Swift host provides a native toggle control and Sidebar menu command, exact Cmd+S routing, a trailing drag grip, left/right keyboard width adjustment and accessibility width actions. Left-edge entry reveals a hidden sidebar without taking page focus. Pointer exit dismisses a transient reveal unless native controls are focused or a menu is tracking; an outside page click dismisses it while preserving the original event. Cmd+T reveals the sidebar before requesting native address focus. The hidden content subtree and resize grip are hidden from accessibility and retain a usable layout width rather than compressing into the tracking edge. Attach/detach own the event monitors, menu and notification observers.

The engine adds the authored experimental `bato_native_slot_set_sidebar_v1(token, width, mode)` export: mode 0 is hidden edge, 1 is docked and 2 is transient overlay. The matching client resolves nine authored engine exports. `BatoSwiftWorkspaceConfigure` now has ten arguments: the state directory and nine callbacks. The setter validates UI-thread, token, modal, fullscreen, visibility and lifecycle state; it revalidates after page focus and native layout callbacks. Hidden mode leaves the physical host visible for page commands, while disabling native focus and Views traversal into the edge. It does not introduce an exception for unexpectedly hidden hosts or weaken the existing sheet, web-dialog, fullscreen-transition and shutdown guards.

Page corners use `MultiContentsView::SetBackgroundRadii` with a ten-point radius in the opted-in normal window and zero in fullscreen. Chromium’s existing propagation reaches the native contents, DevTools and overlays while retaining its split-specific corner policy. Toolbar, origin UI, extension anchors and split ownership remain Chromium-owned. The complete Arc-style browser chrome and Bato split/Peek features remain separate work; this transient sidebar reveal is not Bato’s page Peek feature.

## Current limits

Geometry changes are immediate; no transition animation or persisted width/visibility preference is implemented. Exiting a transient sidebar while a native menu is tracking can leave it open until another exit or outside click. Runtime acceptance covers the recorded dark normal-window geometry, accessibility width actions and steady-fullscreen restoration. General window resize/minimum sizing, light appearance, broader accessibility navigation and split/extension behavior remain unverified here. The fullscreen shortcut fix uses the AppKit fullscreen style bit; transition-time ordering while that bit lags has source review only and is not accepted by the steady-fullscreen check. Existing release, Keychain, signing, security and performance gates remain open.
