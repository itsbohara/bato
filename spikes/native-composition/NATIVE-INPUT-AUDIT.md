# Native input and accessibility boundary audit

Date: 2026-10-28. Read-only inspection of the downloaded Chromium `156.0.8078.48` source, commit `d0c02bfad08ec92a6ffcf989e53cd995e6381a4c`, and CEF `4fa4ab516dacf6c49fc7e6e70d2b7ebce29fa35f`. No source edits, compilation or UI tests were performed for this audit. The coordinator's engine build was already running; it was untouched.

## Source findings

The reserved-Views experiment adds Swift-owned native views directly above the existing `window.contentView` children ([NativeBridge.swift](../linked-native-bridge/NativeBridge.swift), lines142–145). This establishes geometry and visible stacking, but does not establish input or accessibility integration.

Chromium's [`NativeWidgetMac::InitNativeWidget`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/widget/native_widget_mac.mm#L270) initializes its window bridge, then requests `CreateContentView` at line347. [`NativeWidgetNSWindowBridge::CreateContentView`](https://github.com/chromium/chromium/blob/156.0.8078.48/components/remote_cocoa/app_shim/native_widget_ns_window_bridge.mm#L819) constructs `BridgedContentView` and installs it as the window content view. CEF's Views window-handle adapter returns the widget's native NSView ([view_util_mac.mm](https://github.com/chromiumembedded/cef/blob/4fa4ab516dacf6c49fc7e6e70d2b7ebce29fa35f/libcef/browser/views/view_util_mac.mm#L45)); Bato then obtains its window.

`BridgedContentView` supplies two relevant policies:

- [`accessibilityChildren`](https://github.com/chromium/chromium/blob/156.0.8078.48/components/remote_cocoa/app_shim/bridged_content_view.mm#L1724) returns only the Views root accessible when available. It does not merge added AppKit children. Its accessibility hit test also delegates to that root.
- [`hitTest:`](https://github.com/chromium/chromium/blob/156.0.8078.48/components/remote_cocoa/app_shim/bridged_content_view.mm#L290) first asks Views for a hit classification. For `kRootView` it returns itself before calling AppKit's normal child traversal. [`NativeWidgetMacNSWindowHost::GetHitTestResult`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/cocoa/native_widget_mac_ns_window_host.mm#L1354) returns that classification for ordinary Views targets; only a `NativeViewHost` target takes the embedded-native-child route. Reserved layout padding is not itself registration of a native target.

These mechanisms explain how visible AppKit children can be absent from AX and plausibly have clicks routed elsewhere. The actual runtime content class and hit result at a tested button remain unmeasured. This source finding is stronger than a generic computer-control hypothesis, but is not a runtime diagnosis by itself.

**Normal native Chrome uses the same underlying pipeline.** [`BrowserNativeWidgetMac`](https://github.com/chromium/chromium/blob/156.0.8078.48/chrome/browser/ui/views/frame/browser_native_widget_mac.h#L41) subclasses `views::NativeWidgetMac`; its constructor invokes that base, and its [`CreateNSWindow`](https://github.com/chromium/chromium/blob/156.0.8078.48/chrome/browser/ui/views/frame/browser_native_widget_mac.mm#L788) delegates to the base before adding Touch Bar behavior. A different NSWindow subclass does not supply a different content-view hosting contract. The one-file normal-window reservation patch therefore cannot, on its own, establish Swift sibling input/AX. The successful separate companion panel has its own AppKit root and does not test this boundary.

## Proposed bounded native-slot contract

This is a proposal, not an implemented API or foundation choice. Keep the existing browser/compositor hierarchy intact and explicitly register only application-owned native slots with the engine:

1. Associate each opt-in slot with one live window, a stable slot token, an owned native root, and engine-authoritative reserved bounds. Reject unsupported remote/app-shim placement rather than passing an in-process pointer across processes. Registration and teardown run on the main/UI thread; defaults retain stock behavior.
2. Attach only that application-owned root. Route hit tests within its visible bounds to its own AppKit descendants before the generic Views route. Preserve browser/titlebar/resize handling outside slots, modal blocking, overlays and extension/permission anchors. An existing `NativeViewHost` is a relevant engine-owned integration pattern to evaluate; arbitrary `addSubview` is not equivalent.
3. Explicitly merge the slot's accessibility subtree with the Views root, with correct parents, order and hit testing. Define focused-element reporting as well: the host's [`GetAccessibilityFocusedUIElement`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/cocoa/native_widget_mac_ns_window_host.mm#L2040) currently delegates to Views. Native text editing, key traversal, accelerators and focus return need a coordinated first-responder contract.
4. Report and update slot geometry through resize, scale/display changes, minimum sizes and fullscreen transitions. Unregister before window destruction and invalidate callbacks when tabs move or a window closes. Do not discover/reparent internal Chromium views, replace its delegates, or apply blanket hit-test/accessibility changes to unrelated children.

This entails an explicit CEF-to-Chromium/native-bridge seam beyond the current layout patch; the audit does not estimate its implementation size.

### Reuse the existing NativeViewHost path first

A more targeted candidate than modifying `BridgedContentView` globally is an opt-in, engine-owned `views::NativeViewHost` placed in the reserved layout, attaching only Bato's own newly created native root. This creates a Views hit-test target of the type already routed to `kSubView`. [`NativeViewHostMac::AttachNativeView`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/controls/native/native_view_host_mac.mm#L123) adds that root to the native hierarchy and registers the host with its window; existing show/hide, bounds and detach handling can be evaluated instead of duplicated. No Chromium-owned native view needs to be discovered or moved.

The existing AX/focus hooks are promising but **plain NSView attachment is incomplete**. [`NativeViewHost::GetNativeViewAccessible`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/controls/native/native_view_host.cc#L273) forwards the wrapper's native accessible into the Views tree. On macOS, [`GetNativeViewAccessible` and `SetFocus`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/controls/native/native_view_host_mac.mm#L324) either use a `ViewsHostableView` adapter or return/focus the raw native root. The generic focus branch does nothing unless that root accepts first responder; a plain NSView containing text fields does not specify which child should receive focus. More critically, [`SetParentAccessible`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/controls/native/native_view_host_mac.mm#L369) does not stitch the parent for a generic NSView.

Therefore evaluate an application-owned Objective-C++ root/adapter conforming to [`ViewsHostable`](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/base/cocoa/views_hostable.h), containing the Swift controls. Its existing contract includes accessible element/parent assignment, first-responder selection, bounds, visibility and detach. The pinned [`AccessibilityParent` unit test](https://github.com/chromium/chromium/blob/156.0.8078.48/ui/views/controls/native/native_view_host_mac_unittest.mm#L219) demonstrates parent assignment and clearing for such an adapter; it does not establish Bato's input or VoiceOver behavior. The interface was designed for WebContents, so lifetime/layer assumptions and its applicability to this native root must be reviewed explicitly rather than copying a WebContents implementation.

This candidate may avoid custom root hit-test/AX overrides while preserving the existing Views tree. It still requires a bounded CEF/engine registration API, an owned host in normal-window layout, complete focus/modal behavior, and the runtime acceptance above. Compare custom `BridgedContentView` overrides only if the registered host cannot meet a demonstrated requirement; no implementation or runtime result is claimed here.

## Smallest next runtime inspection

In one disposable fixture run, log only the content-view class, known native-control membership in the AX children, and whether a hit test at the fixed native button center resolves that button. Use the public views already held by the bridge; do not traverse private compositor internals or log field contents. Observe first responder class and whether it belongs to the known native field after a real click.

Then require actual native action-count change, text editing, focus return to browser content, AX navigation, resize and clean shutdown. Programmatic focus or `performClick` alone is not acceptance. Repeat in the normal Chrome reservation host after its engine build succeeds; visible reserved space alone does not pass input, AX, split or extension-popup behavior.
